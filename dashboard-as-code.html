Grafana + Jsonnet

All Grafana dashboards for the AWS platform generated from Jsonnet using Grafonnet, version-controlled in Git, and deployed via ArgoCD as Kubernetes ConfigMaps. No manual dashboard editing. No dashboard drift. Full review process for every change.

The Problem

Grafana dashboards are config too — treat them like it

Grafana dashboards created via the UI have a fundamental problem: they live outside of Git. They can be edited by anyone with access. There is no review process. They drift between environments — the prod dashboard looks different from staging. When someone deletes a panel "just to try something," it is gone.

The platform treated dashboards the same way it treated everything else: as code. Jsonnet + Grafonnet generates the dashboard JSON. That JSON lives in Git. ArgoCD deploys it as a Grafana provisioning ConfigMap. The Grafana UI becomes read-only for dashboards that matter.

How It Works

Tanka + Grafonnet — dashboards as reusable code

SOP — Create a Grafana dashboard with Grafonnet
1
Scaffold the team folder
Each team gets a folder in the iac-grafana repo, e.g. /tanka/team/skynet/dashboards, holding three template files: dashboards.libsonnet, overrides.libsonnet, and queries.libsonnet. Separating dashboards, queries, and overrides keeps everything reusable.
2
Define the dashboard with Grafonnet
Import Grafonnet and declare the dashboard. This creates the dashboard in the team's Grafana folder — empty, ready for variables and panels.
local g = import 'github.com/grafana/grafonnet/gen/grafonnet-latest/main.libsonnet'; local dashboard = g.dashboard; { argocd: dashboard.new('ArgoCD'), }
3
Add shared variables
Global variables like datasource, project, and application are defined once in variables.libsonnet and imported into every dashboard — so all dashboards share the same filters and behave consistently.
+ dashboard.withVariables([ variables.datasource, variables.project, variables.application, ])
4
Add panels backed by reusable queries
Panels are placed on a grid (height, width, x, y) and pull from queries defined in queries.libsonnet. Here, an ArgoCD applications table driven by a PromQL query over argocd_app_info.
// queries.libsonnet { applications: prometheusQuery.new( '$' + variables.datasource.name, ||| sum(argocd_app_info{name=~"$application"}) by (project, name, health_status, sync_status) ||| ) + prometheusQuery.withFormat('table') + prometheusQuery.withInstant(true), }
5
Tip: prototype in the UI, then codify
A practical workflow: build the dashboard in the Grafana UI first, use the export function to inspect the JSON, then translate it into Grafonnet — extracting reusable panels and queries into the right library files.

Outcomes

What Dashboard as Code delivered

100% dashboards in Git
Every dashboard is version-controlled. Rollback to any previous state in seconds via ArgoCD history.
Identical across environments
Dev, staging, and prod show identical dashboards — the code is the same. No more "works on my Grafana."
PR-reviewed changes
Dashboard changes go through the same review process as code. PromQL correctness checked before it reaches production.
Reusable building blocks
Panels and queries are written once in shared libraries and reused across every dashboard and environment.
