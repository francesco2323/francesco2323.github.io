Cerebro —
AI Platform Operations Agent

An AI agent that orchestrates platform operations tasks across AWS and Kubernetes — automating infra queries, alert triage, and operational decisions that previously required manual intervention or deep platform expertise.

AI Agent Python AWS APIs Kubernetes API LLM Tool Calling Prometheus API

The Problem

Platform expertise shouldn't be a bottleneck

In any platform team, there is a constant pull: engineers with deep expertise get interrupted constantly by questions that sound simple but require knowing a lot to answer correctly. "Is the cluster healthy?" "Why is this alert firing?" "What's the cost of this namespace?" "Which pods are consuming the most memory?"

Cerebro encodes that platform expertise into an AI agent with direct tool access to AWS, Kubernetes, and the observability stack. The agent can answer operational questions, run diagnostics, and surface insights — without paging an expert at 2AM or interrupting the platform team during a release.

The architecture follows deterministic orchestration principles: the agent has explicit tools, explicit guardrails, and well-defined scope. It does not have write access by default — it operates in read + recommend mode, with escalation paths for actions that require human approval.

Agent Architecture

Tools, reasoning loop, and guardrails

Cerebro — Reasoning & Tool Execution Loop
01 →
User query arrives via Slack or CLI — "Why is the energy-service latency high?" or "Show me pod restarts in prod for the last hour"
02 →
LLM reasons over the query and selects the appropriate tool(s): Prometheus query, kubectl describe, AWS Cost Explorer call, CloudTrail lookup, or Grafana annotation API
03 →
Tools execute with scoped read-only credentials. Results returned to the reasoning loop. Multiple tool calls chained if needed — e.g., get pod name → get its metrics → get its IAM role → check recent AWS API calls
04 →
Guardrails check: Is this a write action? Does it affect prod? If yes → format as a recommendation with the exact command to run, escalate for human approval. Cerebro does not self-approve destructive actions.
05 →
Response surfaced with structured output: diagnosis, supporting evidence from tool calls, recommended remediation steps, and relevant runbook links
Prometheus / Grafana Tool
Executes PromQL queries, retrieves SLO burn rates, fetches active alerts, and reads dashboard annotations. Read-only.
Kubernetes API Tool
kubectl-equivalent operations: list pods, describe deployments, get events, check resource usage, read logs. Scoped to read-only RBAC role.
AWS API Tool
Cost Explorer queries, CloudTrail lookups, EC2/RDS/EKS describe calls, CloudWatch metrics. IRSA-scoped read-only IAM role.
Runbook Retrieval Tool
Semantic search over the platform runbook corpus. When an alert fires, Cerebro retrieves the relevant runbook and surfaces it with the diagnosis.

Example Interaction

Cerebro in action — alert triage

Real interaction — EnergyService high latency alert
Q
User query via Slack
@cerebro EnergyServiceHighLatency alert is firing in prod. What's happening?
1
Cerebro queries Prometheus for latency + error rate
Tool: prometheus_query query: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{job="energy-svc",env="prod"}[5m])) Result: p99 latency = 4.2s (threshold: 1.0s)
2
Cerebro checks pod health and recent events
Tool: kubernetes_get_events namespace: energy-prod reason: [BackOff, OOMKilled, Failed] Result: 3x OOMKilled events on energy-svc-7d9f8 in last 15min
3
Cerebro retrieves the matching runbook
Tool: runbook_search query: "OOMKilled high latency energy service" Result: runbooks/energy-service/oom-remediation.md
✓
Cerebro response to Slack
🔴 EnergyService latency alert — Root Cause Identified Diagnosis: 3 pods in energy-prod OOMKilled in last 15min. Pods restarting → cold start → p99 latency spike to 4.2s. Current memory limit: 256Mi | Recommended: 512Mi based on 14d usage. Recommended action (requires human approval): kubectl set resources deploy/energy-svc -n energy-prod \ --limits=memory=512Mi --requests=memory=384Mi Runbook: https://wiki.internal/runbooks/energy-service/oom-remediation Grafana: https://grafana.internal/d/energy-svc?orgId=1

Outcomes

What Cerebro delivers

Faster incident triage
Alert diagnosis that previously took 15–30 min of expert investigation surfaced in seconds with supporting evidence.
Platform ops democratised
Any engineer can ask operational questions without interrupting the platform team. Expert knowledge is now a tool call.
Guardrails prevent accidents
Write actions are recommendations, not executions. Human approval required for anything touching prod. Read-only by default.
Runbooks embedded in triage
Relevant runbook retrieved and surfaced with every alert response — no hunting through wikis at 2AM.
