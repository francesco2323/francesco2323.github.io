EKS GitOps Platform
with ArgoCD

A shared, multi-tenant Kubernetes platform on AWS EKS where ArgoCD is the GitOps engine — syncing application and platform manifests from GitHub into the cluster, and rolling out container images from ECR to EKS without a single manual kubectl apply.

The Approach

ArgoCD as the single GitOps engine

On the AWS platform, ArgoCD is the preferred GitOps solution — it syncs changes from GitHub (and GitLab) into the EKS clusters. ArgoCD itself is deployed via Terraform as a Helm release when the cluster is provisioned, so even the GitOps engine is infrastructure-as-code.

The whole platform is built on ArgoCD's app-of-apps pattern. A single global "app of apps" points at a directory of other ArgoCD Applications and makes them available for sync. One ArgoCD instance runs per EKS cluster, and a strict directory structure keeps manifests organised per environment and per cluster — argocd-manifests/{env}/{cluster}/.

The key design decision: in-house workload apps keep their Helm chart and their ArgoCD App in their own source repo, while cluster-wide components and community charts live in a central manifests repo. This means teams own their own deployment definitions while the platform team owns the shared baseline.

How an image gets from ECR to EKS

The deployment flow, end to end

Container image → running pod in EKS
01 →
CI builds and pushes to ECR. On merge to main, the GitHub Actions pipeline builds the container image and pushes it to the private AWS ECR registry (a dedicated Registry account). The image is tagged with the commit SHA.
02 →
Image tag updated in the Helm chart. The new image tag is written into the workload's Helm values in its own repo — the source of truth for what should be running.
03 →
ArgoCD detects the change. ArgoCD watches the repo via a GitHub App connection. It sees the Helm values changed and computes the diff between desired Git state and live cluster state.
04 →
ArgoCD syncs to EKS. The ArgoCD App — scoped to its Project and deployed in the argocd-workload-apps namespace — renders the Helm chart and applies it. EKS pulls the image from ECR (nodes have ECR pull permissions via their IAM role) and rolls out the new pods.
05 →
Health + sync status visible in ArgoCD. ArgoCD reports sync and health status. The same state is surfaced in a Grafana dashboard built from the argocd_app_info metric, so anyone can see what's deployed where.

Standard Operating Procedure

Onboarding a new in-house workload to ArgoCD

SOP — Deploy an in-house service via ArgoCD + Helm
1
Create the ArgoCD Project (admin)
Project definitions live centrally in the kubernetes-manifests repo under argocd-manifests/{env}/workloads/projects/. The Project scopes what the app is allowed to deploy and where.
2
Connect the source repository (admin)
Repository config lives as a Kubernetes secret labelled argocd.argoproj.io/secret-type: repository. Authentication uses a repository credential template (GitHub App), so no per-repo credentials are stored.
apiVersion: v1 kind: Secret metadata: labels: argocd.argoproj.io/secret-type: repository name: git-my-service stringData: url: https://github.com/ORG/my-service.git
3
Add an app-of-apps namespace for the team
Each team gets an app-of-apps namespace so their ArgoCD Applications are grouped and isolated from other teams. This keeps multi-tenancy clean.
4
Create the ArgoCD App pointing at the Helm chart
The workload's ArgoCD App lives in the service's own repo under argocd-apps/{env}/app.yaml. It belongs to the Project from step 1 and is deployed into the argocd-workload-apps namespace. It points at the Helm chart in the same repo.
apiVersion: argoproj.io/v1alpha1 kind: Application metadata: name: my-service-dev namespace: argocd-workload-apps spec: project: my-service source: repoURL: https://github.com/ORG/my-service.git path: helm/my-service targetRevision: main destination: server: https://kubernetes.default.svc namespace: my-service syncPolicy: automated: prune: true selfHeal: true
5
ArgoCD syncs — verify health
ArgoCD picks up the App, renders the Helm chart, pulls the image from ECR, and deploys. Confirm sync + health in the ArgoCD UI (SSO via Azure) and on the ArgoCD Grafana dashboard.

Outcomes

What this delivered

Git is the source of truth
No manual kubectl apply. ArgoCD reconciles desired Git state against the live cluster and self-heals drift.
Clean multi-tenancy
Teams own their Helm chart + ArgoCD App in their own repo; the platform team owns Projects and the shared baseline.
ECR → EKS, automated
Image built and pushed to ECR by CI, tag updated in Helm values, ArgoCD rolls it out. No human in the deploy path.
Deploy state is observable
ArgoCD sync/health surfaced in a Grafana dashboard from argocd_app_info — single pane of glass for what's live.
ArgoCD manifests & Helm charts on GitHub
app-of-apps configs, ArgoCD Projects, repository secrets, workload Helm charts.
