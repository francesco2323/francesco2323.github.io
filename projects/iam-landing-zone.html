The Challenge

Security that is structural, not procedural

As the AWS platform scaled to serve multiple product teams on AWS EKS, the risk of privilege escalation, accidental public exposure, and untracked resource creation grew with it. The fundamental problem: security enforced by convention breaks the moment a new engineer joins or someone is under incident pressure.

The goal was to build governance at the AWS account and IAM layer so that bad configurations are structurally impossible — not just discouraged. No static credentials. No public S3 buckets. No overly broad IAM policies that survive code review. All of it prevented at the infrastructure layer.

Architecture

Four governance layers, all IaC-managed

AWS Organizations — OU Hierarchy
Account structure designed around environments and blast radius: Root → Workloads OU → (Dev / Staging / Prod child OUs). Security and logging accounts in dedicated OUs. Account vending via Terraform.
SCPs — Guardrails at Org Level
Service Control Policies enforced at the OU level: deny public S3 ACLs, deny unencrypted EBS volumes, deny root account usage, deny disabling CloudTrail, restrict services to approved regions only. Structural — not bypassable by any account admin.
IRSA — Pod-Level AWS Permissions
Every EKS workload that needs AWS access gets an IAM Role for Service Accounts (IRSA). Scoped to exact resources — specific S3 buckets, specific DynamoDB tables, specific SQS queues. No static credentials anywhere on the platform.
Terraform IAM Baseline Modules
Reusable Terraform modules for IAM role creation, IRSA binding, and policy management. Teams onboard by calling the module with their service account name and required permissions — the module handles trust policy, boundary, and tagging automatically.

Design Principles

How we thought about IAM governance

Deny by default, allow explicitly
IAM policies are deny-all at the org level. Every permission is an explicit allow, scoped to the minimum required resource. Wildcards are blocked by policy linter in CI.
Blast radius by account, not by tag
Dev, staging, and prod are separate AWS accounts — not just separate namespaces. A compromised dev credential cannot touch prod resources. SCPs enforce the boundary at the org layer.
IAM changes go through Git and CI
No IAM changes via console. All policies, roles, and IRSA bindings are Terraform — reviewed in PR, validated with tfsec and OPA, applied via the CI/CD pipeline on merge. Full audit trail.
Zero static credentials on the platform
IRSA eliminates all long-lived AWS access keys from EKS workloads. GitHub Actions uses OIDC federation. No secrets in environment variables or Kubernetes secrets for AWS access.

Standard Operating Procedure

Onboarding a new workload to IAM governance

SOP — Adding IRSA for a new EKS service
1
Define the IAM policy — minimum permissions only
Author a Terraform module call specifying only the exact resources and actions the service needs. No wildcards. Policy validated by tfsec and OPA Conftest in CI before any apply.
module "my_service_irsa" { source = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts-eks" role_name = "my-service-prod" oidc_providers = { main = { provider_arn = module.eks.oidc_provider_arn namespace_service_accounts = ["my-namespace:my-service-sa"] } } # Minimum required permissions only role_policy_arns = { policy = aws_iam_policy.my_service.arn } }
2
CI validates the plan against SCP and OPA policies
GitHub Actions runs tfsec (static analysis), tflint (best practices), and Conftest (OPA policy validation on the Terraform plan JSON). Any wildcard resources, missing boundary policies, or missing tags fail the pipeline.
tfsec ./iam/ tflint --recursive terraform plan -out plan.tfplan terraform show -json plan.tfplan | conftest test - --policy ./opa-policies/iam/
3
Merge to main triggers the deploy pipeline
After CODEOWNERS review and a green CI run, the PR is merged. The CI/CD pipeline applies the Terraform. The IAM role ARN is then referenced in the workload's Helm values for the Kubernetes ServiceAccount annotation, binding the pod to its IRSA role.
# Kubernetes ServiceAccount annotation (in Helm values) serviceAccount: annotations: eks.amazonaws.com/role-arn: arn:aws:iam::ACCOUNT_ID:role/my-service-prod
4
Verify IRSA is working — no static credentials
Confirm the pod receives temporary STS credentials via the projected service account token. Verify no AWS_ACCESS_KEY_ID environment variable exists. Check CloudTrail for the assumed role events.
kubectl exec -n my-namespace my-pod -- env | grep AWS # Expected: AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE # NOT expected: AWS_ACCESS_KEY_ID aws cloudtrail lookup-events \ --lookup-attributes AttributeKey=Username,AttributeValue=my-service-prod

Outcomes

What this delivered

Zero static credentials on platform
IRSA + OIDC federation eliminated all long-lived AWS access keys from EKS workloads and GitHub Actions.
Blast radius by account
Dev, staging, prod in separate accounts. SCP guardrails at OU level — structurally impossible to cross environments.
Full IAM audit trail from Git
Every IAM change is a reviewed PR with Terraform plan. No console changes. Compliance evidence requires no additional tooling.
Self-service onboarding
Teams call the IRSA Terraform module — IAM role, trust policy, and boundary are handled automatically. No platform team bottleneck.
