The Problem

A repeatable response, not improvisation

When something breaks in production, the worst time to decide how to respond is during the incident. The incident management system exists so that response is structured and repeatable — a clear severity classification, a defined process with named roles, and per-service runbooks that turn expert knowledge into steps anyone on-call can follow.

The guiding principle, written into the severity doc itself: "Always assume the worst." If you are unsure whether something is a SEV-2 or a SEV-1, treat it as the higher one. An incident is not the time to litigate severity — assume the highest, then review during the post-mortem.

Severity Model

SEV-1 to SEV-5 — classification drives response

Lower numbers are more urgent. Anything above SEV-3 is automatically a "major incident" and triggers the full incident response process.

The Process

Detection → Triage → Escalate → Response

Incident management process
1 →
Detection. Through monitoring & alerting, customer/partner reports, or internal reports. Once detected, an Incident Commander (IC) is appointed — automatically via on-call schedules, or manually if needed.
2 →
Triage. The IC answers three questions: Is this actually an incident? What severity is it (assume the worse if unsure)? Is anything urgent to expedite before escalating — e.g. block network access if data is being exfiltrated?
3 →
Escalate. For major incidents (SEV-1/2), involve BCM. Open an incident on Statuspage. Spin up a video call in the MS Teams Incident Management channel with a clear title like [SEV-1] Firewall down, kicked off with the declaration template. Assign Deputy IC, Scribe, and gather SMEs as available.
4 →
Response. The IC leads — delegating tasks to the Deputy, Scribe, and SMEs — and orchestrates the steps needed to resolve. Runbooks for the affected service guide the hands-on remediation.
5 →
Resolution & Post-Mortem. Once resolved, a blameless post-mortem captures root cause and follow-up actions — using the post-mortem template. Real examples in the repo include a SEV-2 firewall deny and a SEV-4 prod resource deletion by terraform apply.

Runbook Anatomy

Every runbook follows the same structure

Consistency is what makes runbooks usable at 2AM. Each one — for example, RDS High CPU Utilization — follows the same sections so an engineer always knows where to look.

Runbook: RDS High CPU Utilization
Meaning
What the alert actually means — high CPU on RDS/Aurora PostgreSQL signals the instance is consuming a large share of its processing resources, often from intensive queries, a surge in connections, inefficient queries, or autovacuum.
Impact
Why it matters — performance degradation and higher latency, connection timeouts or failures, and in extreme cases an unresponsive instance.
Diagnosis
Where to look and what to run — start from the linked Grafana RDS dashboards (dev / staging / prod), then drill in with Performance Insights and native PostgreSQL queries.
-- Long-running queries (>5 min) SELECT pid, usename, application_name, state, query, now() - query_start AS duration FROM pg_stat_activity WHERE state = 'active' AND now() - query_start > interval '5 minutes'; -- Top queries by total execution time SELECT query, calls, total_exec_time, rows FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;
Mitigation
How to bring it back — optimise inefficient queries and add indexes, manage connections with pooling, scale vertically or add read replicas, and keep vacuum/analyze healthy.
Escalation
Who to involve and when — a tiered L1 → L2 → L3 path, below.
L1
First response. Monitor alerts, gather metrics from Grafana, perform initial troubleshooting steps.
L2
Analysis. Dig into system and application logs, identify root cause, apply configuration changes or patches.
L3
DevOps / SRE. Advanced diagnostics and deep dives; coordinate with AWS Support for underlying infrastructure issues.
